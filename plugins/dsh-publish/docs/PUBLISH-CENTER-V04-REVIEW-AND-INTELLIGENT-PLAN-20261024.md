## 1. 审核结论与最新需求

**原方案需要修改后再实施。用户明确补充：不需要 Park 的“打包”，需要更智能化的方案。** 因此删除“内容工作台 = Park 打包”的产品定位，不以 ZIP、五平台表单、固定六标题候选作为主流程。

建议定位为：**一个插件内的智能发布助手，接收已有内容，理解素材，推荐发布方式，生成平台版本，检查缺项，引导人完成发布并留下记录。** 智能化的验收标准是减少重复输入和人工检查，而非增加表单与生成按钮。

沿用当前待审方案中的人机分工：AI 负责发布前准备，用户在平台完成最终发布；此次补充没有提出恢复自动代发。旧自动引擎按兼容需要保留为独立实验能力。这里是实施建议，不是要求用户再确认一次。

Park 调研可作为人工发布的参考资料；不再作为整个插件的结构模板。尤其不能把“不代发”写成消除全部平台风险，也不能把“使用浏览器登录态”写成无需登录平台。

## 4. 新主流程：智能发布助手

### 4.1 从已有内容开始

首页只有一个主要入口：“这次要发什么？”支持粘贴成稿、选择 Markdown/TXT/SRT 文件、附加图片或视频。也可以说：“把这篇发到小红书和公众号，保留我的说话方式。”

首版优先完成文字成稿和 SRT 的可靠解析；已有视频可附上对应字幕。视频没有字幕且未接入转写时，显示“尚未读取视频内容”，允许补字幕或使用现有文字继续。文件名、路径和媒体类型不能作为“已理解内容”的证据。

从 Obsidian 或其他创作产物进入时，记录来源文件及读取时的版本；不要求重新粘贴。仅读取用户本次选择的文件与明确配置的资料范围，避免扫描整个知识库。此插件负责发布前适配，不重建选题、对标研究、拍摄或剪辑流程。

### 4.2 先理解，再推荐

AI 先展示一个简短理解：“这篇讲什么、面向谁、哪些事实已有依据”。随后给出建议平台和形式及理由，用户可以调整；不会每次强制生成全部五个平台。

对缺少事实的问题，只问影响当前结果的一项，例如“这里提到提升了效率，有具体例子吗？”用户也可跳过，生成不含该断言的版本。禁止为了补足文案编造数据、个人经历或引用。取消机械的“至少 40 字”要求。

推荐采用“规则判断 + AI 建议”：平台支持形式、字段限制由规则检查，内容适合度由 AI 解释。不要给没有数据依据的爆款概率或确定性效果承诺。

### 4.3 为选定平台生成可用版本

每个平台默认一个推荐稿，显示“改了什么、为什么”。备选标题按需展开，不要求用户从三十个标题中逐个挑选。

| 发布形式 | 应生成或保留的字段 |
|---|---|
| 视频描述 | 开头、描述、话题、关联视频与封面状态；字段按平台实际表单配置 |
| 小红书图文 | 标题、正文、话题、图片顺序与缺图提示 |
| 公众号文章 | 标题、独立摘要、文章结构与正文、可复制的排版版本、封面及配图状态 |
| X 标准短帖 | 完整短帖、媒体关联、加权字符数；不强塞独立标题字段 |

首版能整理已有图片和封面，不能把“缺封面”显示为“已生成封面”。封面设计、图片生成和视频转写作为后续可插拔能力，接入前显示实际支持范围。

支持定向修改：“只改小红书开头”“公众号保留原文，不扩写”“三个平台都少一点推销口吻”。执行前识别修改范围，生成结果先作为候选；用户手改过的字段不得被后台悄悄替换。提供差异预览、接受和撤销；部分平台失败时保留其他平台的结果。

### 4.4 AI 检查与规则检查各负其责

规则检查字段长度、必需媒体、形式兼容性、已保存状态。AI 检查标题是否夸大、正文是否出现无来源数据、内容与素材是否一致，并指出原句或字幕时间。AI 检查属于建议，不包装成平台审核保证。

首页显示可执行的缺项，例如“公众号还缺封面”“小红书标题超出已核实限制”“视频正文尚未读取”。每项都能跳到对应字段，或生成修改建议。硬限制不满足时不能标为“准备完成”，但仍允许保存、编辑和复制内容用于修正。

### 4.5 人工发布与结果记录

准备完成的平台卡提供对应字段复制、媒体查看或导出、打开平台后台。公众号提供富文本和纯文本复制，说明图片仍需在平台上传；平台字段分开时，不承诺一次粘贴自动填满所有字段。

桌面使用已支持的宿主方式打开系统浏览器；Web 使用明确的新标签页行为。二者需分别验证，不能把 Web 新标签页等同于系统默认浏览器。平台入口经过白名单校验，具体上传页随平台可用性维护。

复制成功只记录复制动作，打开后台只记录打开动作，均不推断已发布。用户逐平台点击“标记已发”，确认所用版本，可补时间、作品链接及平台上实际修改的内容；允许不填链接，界面注明“人工标记，未核验”。

已发布历史固定绑定确认时的快照。后续改稿创建新版本；撤销标记只纠正本插件记录，不删除平台作品。同一内容在不同平台、不同发布批次分别记录。手动记录不复用自动引擎的 unknown 状态，但不能因此声称平台结果已被验证。

## 5. 页面与设置的详细对应

一个插件内保留四个区域：智能发布、草稿、发布记录、设置。平台卡片顺序沿用现有拖拽能力；首页优先显示本次要完成的事，不默认铺开五张空白表单。

下面是下一版建议配置；除 showSidebar、homeCards 等现有字段外，新增项不代表现在已经存在。

| 设置 | 建议默认值 | 页面行为与执行要求 |
|---|---|---|
| 显示侧边栏入口 | 开，沿用 showSidebar | 立即增删入口；不卸载插件，不删除草稿，设置中仍可打开发布页 |
| 默认打开页面 | 智能发布 | 仅控制发布插件内部首页，不改整个 DSH 应用启动页 |
| 常用平台与顺序 | 可配置五平台，保留已有顺序 | 生成前作为推荐初值；本次取消平台不自动删除长期偏好 |
| 默认发布形式 | 各平台分别保存 | 只作为初值；AI 发现不适配时提示，不能静默替换用户选择 |
| 默认模型 | 跟随已配置的 DSH 模型路由 | 显示实际模型；缺模型给配置入口，不另存 API Key，不暗用其他模型 |
| 个人风格资料 | 未选择时使用当前素材 | 用户选文件或模板；显示实际读取的资料及版本，避免固定“公众号必须正式”等假设 |
| 平台规则与建议 | 内置已核验版本 | 展示来源、日期、单位；用户偏好单独配置，不能把未知限制改成硬拦 |
| 自动保存 | 默认开启 | 展示“保存中／已保存／保存失败”，失败保留内容并能重试；不要以关闭页签作为唯一保存机制 |
| 草稿与附件位置 | 沿用 DSH 数据目录策略 | 可查看位置、导出单条、检查缺失文件；清理前说明影响，不按过期时间静默删稿 |
| 小红书数据读取 | 单独显式启用 | 说明需要现有上游服务及登录态；未启用不自动查账号或读数，失败不影响手动发布 |
| 实验：自动发布 | 新模式默认关；旧配置迁移需明确告知 | 配置账号、引擎地址、令牌、审批等仅在实验区域出现；后台与工具同步检查，不影响人工助手 |

保留旧 publishingEnabled 的现有语义，不能直接把“停用自动提交”解释为“禁止生成和复制”。新实验开关应明确命名并定义与旧开关的关系；迁移不得删除账号配置、旧任务、回执或 unknown 记录。历史查看不应要求先开启自动发布。

## 6. Qoder 的实现约束

1. **复用现有插件。** 页面、设置与业务实现都在 dsh-publish 内；Host 业务服务供页面和聊天使用。聊天可以创建草稿、生成与修改候选，不能调用“人工标记已发”。不修改 DSH 核心循环来实现本功能。
2. **先验证模型接入。** 使用 DSH 已配置模型及受支持的调用路径，查清 provider/model 路由、流式输出、取消和会话日志如何保存。当前源码未证明新增页面只调用 ctx.llm 就能自动获得这些能力；不能只保存最终文案而丢掉模型输入记录。
3. **保存完整生成依据。** 记录所选素材版本、提示词与平台规则版本、实际模型、生成请求与结果，遵守 DSH“模型可见内容可由会话日志重建”的要求；不把凭据写入输入或快照。
4. **按版本保存。** 至少区分素材版本、平台草稿、生成任务、人工确认记录和偏好设置。保存请求带预期修订号，服务端拒绝陈旧覆盖；生成返回前若用户已改稿，只能提供候选或显示过期结果。
5. **失败能恢复。** 本地缓存按 profile、草稿和平台隔离，不存媒体大文件。服务端写入成功才显示已保存；缓存不可用、磁盘写入失败、页面刷新、切换草稿均要有可见结果，避免承诺“永不丢字”。发布快照须先持久化，再返回确认成功。
6. **AI 输出按形式校验。** 分平台任务可独立取消、失败、重试；重试限额与请求身份明确，已经成功的结果不全部重跑。结构校验通过不等于事实与平台规则校验通过；前后端共用已核验规则，生成按钮禁用不能替代服务端并发控制。
7. **关闭实验是真正关闭。** 自动 prepare/submit 及已排队任务在执行前检查最新开关；关闭后不启动新引擎操作。已有外部提交不能假定可以撤回，保留真实结果与未核验状态。模型不再看到可执行的自动发布工具，旧客户端请求也应被拒绝。只读历史可以保留。
8. **显式适配数据回采。** 当前 metrics.bind 依赖旧 prepareId 和账号笔记列表，新手动记录需要独立的关联对象及权限检查；不要伪造一次自动预检来获得 prepareId，也不要按标题相似度直接认定作品归属。
9. **兼容旧数据。** 新增草稿与手动记录优先使用独立且有版本的存储，保留旧台账读取与展示。若修改已发布持久类型，按 DSH 对应规则声明、迁移并测试；产品文字使用现有中英字典。

## 7. 后续实施顺序与交付证据

不要将“无 AI 的五平台表单”作为首个业务交付。技术基础可先施工，但首个业务验收必须体现智能化。

| 批次 | 工作范围 | 必须交付的证据 |
|---|---|---|
| 0：接入验证与方案落定 | 模型路由与日志验证、素材选择与保存验证、确定平台字段和规则依据、补页面草图 | 一条实际接入验证记录、支持范围、字段与数据设计；据此重新估工期 |
| 1：智能最小闭环 | 文字／SRT 输入；选择两平台；AI 适配、缺项检查、定向改稿；自动保存；字段复制与打开后台；逐平台人工记录 | 首先以小红书＋公众号验收：一份素材生成两个不同结构版本，改稿不覆盖，刷新能恢复，确认版本可追溯 |
| 2：五平台与设置完整性 | 扩展抖音、视频号、X；X 加权计数；侧边栏、默认页、平台顺序和实验开关；旧数据展示 | 五平台字段与入口核验记录，设置行为测试，实验关闭后的后台拒绝测试，旧历史兼容测试 |
| 3：媒体理解增强 | 接入实际可用的视频转写、图片理解、封面或配图能力 | 每项标明模型或工具依赖、耗时、取消、费用及失败恢复；未接入项不冒充已完成 |
| 4：复盘建议 | 手动记录关联数据、人工填数、基于真实历史提出下一次调整 | 数据来源和采集时间明确；无数据时显示未知，建议不伪装成因果结论 |

原方案的“2–3 天 + 2 天”未覆盖媒体读取、版本保护、模型日志和实验禁用的验证，不能原样承诺。Qoder 在批次 0 后按实际复用程度给出估算；媒体增强和复盘独立估算，不阻塞文字发布闭环。

## 8. 验收清单

- 一份已有 Markdown 或 SRT 能进入助手；模型确实收到内容，来源可追溯；没有转写时不声称读懂视频。
- 首版至少两个平台得到符合各自字段的版本，公众号摘要与正文分开；推荐理由不是固定平台语气套话。

- 侧边栏隐藏后设置仍能打开插件；关闭自动通道后，页面、工具、旧请求和排队任务均不能开始新的自动发布；历史继续可查。
